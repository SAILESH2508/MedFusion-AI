# MedFusion AI — 6-Feature Enhancement Implementation

This PR adds six features to an existing Django + React medical platform: a Biomarker Trend Timeline, Explainable Risk panels, a What-If Risk Simulator, Emergency QR generation, Multilingual/Voice explanation, and a Light/Dark theme system. The implementation reuses the existing architecture (RandomForest ML models, Gemini translation, React Router, custom CSS variables) without introducing new dependencies. Django `manage.py check` passes with zero issues; Vite production build completes without errors.

**Watch for:** `get_emergency_card` returns `"name"` but `EmergencyCard.jsx` reads `data.patient_name` — the patient name will always display as "Unknown" on every scanned QR card. This is a confirmed bug that silently degrades the primary emergency use case.

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The theme system is solid: `ThemeContext.jsx` stores the user's preference in `localStorage`, applies `data-theme` on `<html>`, and both `[data-theme='dark']` and `[data-theme='light']` blocks are present in `index.css`. The Navbar correctly renders `Sun`/`Moon` toggle buttons in both desktop and mobile nav.

The Explainable Risk and What-If Simulator both live correctly in the prediction result panels of `PatientDashboard.jsx` and `GuestDashboard.jsx`. Feature importances come from `model.feature_importances_` via `_predict_using_ml`, not from Gemini. The simulator posts to `/predictions/simulate/` and never creates a `PredictionRecord`. Medical disclaimers are present in both panels.

The Biomarker Trend Timeline is computed client-side from the `archive` prop already passed to `MedicalVault.jsx`. Directionality labels (Improving/Worsening/Changed/Stable) are guarded by a conservative `LOWER_IS_BETTER`/`HIGHER_IS_BETTER` set — ambiguous biomarkers fall through to "Changed". The SVG chart renders for ≥2 data points.

The Emergency QR flow has a field name mismatch: `get_emergency_card` returns `"name"` in the JSON response, while `EmergencyCard.jsx` reads `data.patient_name`. Every live scan will show "Unknown" where the patient name should appear. The rest of the emergency card fields (`vault_id`, `blood_group`, `allergies`, `active_meds`, `emergency_contact`, `last_updated`) are correctly mapped. The token endpoint never returns JWT, email, or password — it returns only `{token, url}`. The public card endpoint requires no auth, consistent with the QR emergency access requirement.

The `VoiceExplainer` component checks `window.speechSynthesis` before using it and renders a "Voice not supported in this browser." message when absent. Translation calls `POST /api/ai/explain/` with `{text, language}` and falls back to original text on error. The component is wired into `PatientDashboard`, `GuestDashboard`, and `MedicalVault` pathology summary panels.

### Emergency card name field mismatch

`get_emergency_card` in `views.py` (line 1165) returns:

```python
"name": f"{patient.first_name} {patient.last_name}".strip() or patient.user.full_name or "Patient",
```

`EmergencyCard.jsx` (line 83) reads:

```jsx
<span style={styles.valueLarge}>{data.patient_name || 'Unknown'}</span>
```

`data.patient_name` is always `undefined` against this response shape, so the rendered card always shows "Unknown" for the patient name. The other five fields (`vault_id`, `blood_group`, `allergies`, `active_meds`, `emergency_contact`, `last_updated`) are correctly mapped. The fix is a one-line change in either file. — **confirmed**

### Simulator fallback deviates from ML model

When `_predict_using_ml` returns `None` (model file not found or inference error), `simulate_prediction` falls back to an inline rule-based score. This is consistent with `predict_health_risk`'s own fallback and the approach is acceptable, but the response sets `factors: []` in this case, which means the simulator result panel will show "Factor breakdown not available" even though a numeric score is returned. This is a UX gap rather than a data integrity issue — no fake ML results are presented. — **confirmed**

### VoiceExplainer stale translation on prop change

When `language !== 'en'` and the parent re-renders with a new `text` prop (e.g., after a second prediction run), `useEffect` does not trigger a re-translation — the old translated string persists until the user manually switches language. In practice the `text` prop is a completed prediction's `clinical_reasoning` that doesn't change mid-session, so the window is narrow, but a user who runs two predictions without navigating away will see the first prediction's translation under the second prediction's result if they stay on a non-English language. — **possible**
